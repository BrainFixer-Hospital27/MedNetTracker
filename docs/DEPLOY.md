# Развёртывание на сервере

Приложение упаковано в Docker. Ниже — три способа доступа, от самого
защищённого к самому открытому, и подробности по обслуживанию.

---

## Сначала о главном: какой доступ выбрать

В базе лежат MAC-адреса, планы этажей, схема подключений и пароли от
роутеров и точек доступа. Приложение проектировалось под изолированную
сеть: пароли сетевого оборудования хранятся открытым текстом, потому что
в той модели угроз шифрование при одном ключе на том же сервере давало
бы лишь видимость защиты.

На публичном адресе модель угроз другая. Поэтому:

| Способ | Когда подходит |
|---|---|
| **Только через WireGuard** | реальные данные больницы. Рекомендуется |
| **Cloudflare Tunnel + Access** | нужен доступ без VPN, но с проверкой личности |
| **Публичный домен** | тестирование на демонстрационных данных |

Умолчание в `docker-compose.yml` — первый вариант. Снять ограничение
проще, чем потом спохватиться.

## Подготовка

```bash
git clone <репозиторий> mednet-tracker    # либо распакуйте архив
cd mednet-tracker

cp .env.docker.example .env
```

Заполните в `.env` два обязательных значения:

```bash
# пароль администратора
ADMIN_PASSWORD=...

# ключ подписи сессий
SESSION_SECRET=$(openssl rand -hex 32)
```

Создайте каталог данных **до** первого запуска и передайте его
пользователю контейнера:

```bash
mkdir -p data/svg
sudo chown -R 1000:1000 data
```

Это важно. Контейнер работает не от root (пользователь `node`, uid 1000),
а Docker при монтировании создаёт отсутствующий каталог от root — и
приложение не сможет писать в базу. Если пропустить шаг, при запуске
увидите понятное сообщение с этой же командой.

## Вариант 1. Доступ только через WireGuard

Узнайте адрес сервера внутри туннеля:

```bash
ip addr show wg0 | grep inet
```

Пропишите его в `.env`:

```bash
BIND_ADDRESS=10.13.13.1     # ваш адрес в туннеле
PUBLIC_PORT=3000
TRUST_PROXY=0
COOKIE_SECURE=0
```

Запуск:

```bash
docker compose up -d --build
docker compose logs -f mednet
```

Приложение будет доступно на `http://10.13.13.1:3000` с любого
устройства, подключённого к туннелю. На публичном интерфейсе порт не
появится — проверить можно с другой машины:

```bash
nmap -p 3000 ваш.домен      # должно быть filtered или closed
```

Если WireGuard у вас работает в контейнере и интерфейс `wg0` создаётся
внутри его сетевого пространства, привязка к `10.13.13.1` на хосте не
сработает. Тогда либо подключите приложение к сети того же контейнера
(`network_mode: "service:wireguard"`), либо привяжите к `127.0.0.1` и
пробросьте через nginx, слушающий на адресе туннеля.

## Вариант 2. Cloudflare Tunnel

Доступ по домену без единого открытого порта: `cloudflared` сам
устанавливает исходящее соединение с Cloudflare. Дополнительно можно
включить Cloudflare Access — тогда перед приложением встанет проверка
личности по почте или через ваш провайдер входа.

В `.env`:

```bash
BIND_ADDRESS=127.0.0.1
TRUST_PROXY=1
COOKIE_SECURE=1
REAL_IP_HEADER=cf-connecting-ip
```

Добавьте в `docker-compose.yml`:

```yaml
  cloudflared:
    image: cloudflare/cloudflared:latest
    container_name: mednet-tunnel
    restart: unless-stopped
    command: tunnel --no-autoupdate run --token ${TUNNEL_TOKEN}
    depends_on:
      - mednet
```

Токен берётся в панели Cloudflare, раздел Zero Trust → Networks →
Tunnels. Там же настраивается маршрут: `mednet.вашдомен.ru` →
`http://mednet:3000`.

Обратите внимание: при таком подключении контейнеры общаются по
внутренней сети Docker, поэтому в `ports` приложение публиковать не
нужно вовсе — уберите этот раздел.

## Вариант 3. Публичный домен через nginx

Только для тестирования на демонстрационных данных.

В `.env`:

```bash
BIND_ADDRESS=127.0.0.1
TRUST_PROXY=2               # Cloudflare + nginx
COOKIE_SECURE=1
REAL_IP_HEADER=cf-connecting-ip
```

Конфигурация nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name mednet.вашдомен.ru;

    ssl_certificate     /etc/ssl/cloudflare/origin.pem;
    ssl_certificate_key /etc/ssl/cloudflare/origin.key;

    # Планы этажей со вшитой растровой подложкой бывают увесистыми.
    # Значение по умолчанию — 1 МБ, загрузка сорвалась бы с ошибкой 413.
    client_max_body_size 40m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header CF-Connecting-IP  $http_cf_connecting_ip;

        # Сборка книги отчётов на большой базе занимает секунды
        proxy_read_timeout 120s;
    }
}
```

В панели Cloudflare:

- режим шифрования **Full (strict)** с сертификатом Origin Certificate;
- правило кеширования: **не кешировать** `/api/*` — иначе браузер
  получит чужие или устаревшие данные;
- при желании — правило Rate Limiting на `/api/auth/login`.

Приложение отдаёт статику с `Cache-Control: no-cache`, так что
обновления доезжают сразу; трогать настройки кеша Cloudflare для
остальных путей не требуется.

## Обслуживание

### Резервное копирование

Всё состояние приложения — в каталоге `data`. Снимок базы снимается на
работающем сервере, останавливать ничего не нужно:

```bash
docker compose exec mednet npm run backup
```

Команда использует `VACUUM INTO` — согласованный снимок базы в режиме
WAL. Простое копирование файла так не умеет: часть данных может остаться
в журнале.

Ежедневное копирование через cron:

```cron
30 3 * * * cd /opt/mednet-tracker && docker compose exec -T mednet npm run backup \
  && tar czf /var/backups/mednet-$(date +\%F).tar.gz data/ \
  && find /var/backups -name 'mednet-*.tar.gz' -mtime +30 -delete
```

Планы этажей лежат отдельными файлами в `data/svg` — архив выше
захватывает и их.

### Обновление

```bash
cd /opt/mednet-tracker
docker compose exec mednet npm run backup     # на всякий случай
git pull                                       # либо распакуйте архив
docker compose up -d --build
```

База переживает обновление: она в примонтированном каталоге. Недостающие
столбцы приложение добавляет само при запуске.

### Проверка состояния

```bash
docker compose ps                    # состояние контейнера
curl -s localhost:3000/healthz       # ответ приложения
docker compose logs --tail=50 mednet
docker stats --no-stream mednet      # память и процессор
```

Расход памяти под нагрузкой — около 90 МБ. Предел в `docker-compose.yml`
поставлен на 256 МБ: этого хватает с запасом, а на сервере с гигабайтом
памяти важно, чтобы соседние контейнеры не остались без ресурсов.

### Ревизия данных

```bash
docker compose exec mednet npm run check          # отчёт
docker compose exec mednet npm run check -- --fix # исправить
```

## Что стоит проверить после запуска

1. `curl -s https://mednet.вашдомен.ru/healthz` отвечает `{"status":"ok"}`.
2. Вход работает, после перезапуска контейнера сессия сохраняется
   (значит, том смонтирован верно).
3. Загрузка плана этажа проходит — это проверка ограничения на размер
   тела запроса.
4. Книга отчётов скачивается целиком.
5. Порт приложения **не** виден снаружи, если выбран доступ по VPN.
6. Отметки времени в журнале изменений совпадают с местным временем —
   иначе поправьте `TZ` в `.env`.

## Известные ограничения при работе через интернет

Это стоит держать в голове, если решите оставить публичный доступ
надолго с реальными данными.

**Пароли сетевого оборудования хранятся открытым текстом.** Осознанное
решение для изолированной сети. Для публичного размещения его следовало
бы пересмотреть — но честное шифрование требует ключа, который не лежит
на том же сервере, то есть ввода мастер-пароля при каждом запуске.

**Одна учётная запись без второго фактора.** Защита от подбора есть
(нарастающая задержка и блокировка адреса на пять минут), но это не
замена двухфакторной проверке. Cloudflare Access закрывает этот пробел
внешними средствами.

**Нет защиты от подделки межсайтовых запросов.** Кука помечена
`SameSite=Lax`, что закрывает основные сценарии, но выделенного токена
в формах нет.

Если публичный доступ понадобится постоянно — скажите, эти три пункта
закрываются за разумное время.
